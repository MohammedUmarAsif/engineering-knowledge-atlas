# Start Here

## Your operating rule

Reading is useful only when it changes what you can explain, notice, or decide. Do not measure progress by pages opened.

For each module:

1. Attempt its diagnostic aloud, without notes.
2. If every answer is precise, follow **Skip to**.
3. If an answer is vague, read from the beginning.
4. Write a short explanation in `notes/concept-notes/` using your own words.
5. Apply the senior and production lenses.
6. Mark the module `revisit`, `working`, or `mastered` in your private notes.

## What counts as mastery?

You can:

- explain the concept simply and technically;
- identify its assumptions and failure modes;
- compare it with alternatives;
- reason about security, reliability, latency, and cost;
- diagnose a realistic production problem;
- connect it to adjacent concepts;
- say what evidence would change your decision.

Recognition is not mastery. If an explanation collapses without familiar terminology, read the module.

## Code while reading

Python examples are primary in the AI pathway; C++ companion examples expose typing, ownership, error handling, and systems trade-offs. In game modules, C++ becomes primary. Read the explanation first, predict the code's behavior, then run or modify it on the main development computer.

## Reading modes

### Survey

Build the map. Read headings, mental models, and connections.

### Study

Read carefully, follow primary sources, and create notes.

### Interview

Answer diagnostic, trade-off, and incident questions aloud under time pressure.

### Research

Trace claims to papers, inspect methods and limitations, and map disagreements.

## Source hierarchy

Prefer, in order:

1. Specifications and standards
2. Official documentation
3. Peer-reviewed papers and canonical textbooks
4. University course material
5. Engineering reports and postmortems
6. High-quality secondary explanations

Blogs and videos can clarify a concept but should not be the sole authority for an important claim.
